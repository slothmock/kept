# Superseded — Kept MVP Implementation Stages

> **Status:** Superseded by the vault-only direction selected on 12-Sep-2026. Do not implement stages below without an explicit new decision.
>
> **Current direction:** one Monad USDC savings vault, permanently bound to one Aave strategy. Privy remains for consumer authentication/accounts and sponsored actions; Aurora Intents remains a future funding integration. Commitments, proofs, trust scoring, reward programmes, `RewardController` product work, and automatic saving are deferred. No performance-fee contract feature has been approved.

**Goal:** Turn the existing tested savings, reward, catalogue, and persistence foundations into a demoable Kept MVP with one coherent consumer journey and real Privy/Aurora integrations.

**Architecture:** Keep the accepted modular-monolith shape: one TypeScript API, one web app, PostgreSQL for private workflow metadata, and exactly three deployed Kept contracts. Financial state remains chain-authoritative; the backend stores private metadata, verification workflow, idempotency, and chain projections only.

**Starting point (verified 12-Sep-2026):** `npm run typecheck` and `npm test` pass (129 TypeScript tests). Foundry passes 59 local/mock/fuzz/invariant tests; its one Monad/Aave fork test is skipped until `MONAD_RPC_URL` is configured. The repository has no tracked `apps/web`, no HTTP/API runtime, no Privy, Intents, proof-adapter, trust-engine, or deployment implementation.

**Non-negotiable MVP boundaries:**
- Three commitment paths only: weekly savings, verified activity count, social study sessions.
- Native Monad USDC only; one permanently bound Aave strategy.
- Exactly three deployed Kept contracts: vault, strategy, reward controller.
- Rewards are separate, pre-funded USDC and remain bounded by `RewardController`.
- No behavioural labels, raw evidence, social graph, or verifier identities onchain.
- Automatic saving must be restricted both by Privy policy and vault-enforced seven-day cadence.
- The Aurora / NEAR Intents path settles into the user's Monad account before the vault deposit.

## Stage 1 — Expose the existing private-goal and commitment flow as an authenticated API

**Outcome:** A real client can create/read goals and create/activate commitment drafts through authenticated, versioned HTTP endpoints.

**Work:**
1. Choose and add one minimal HTTP framework; do not introduce a second service or a frontend-specific backend.
2. Create application bootstrap, configuration validation, request logging, structured error mapping, and a health endpoint.
3. Add Privy token verification middleware. Map authenticated Privy identity to an internal user id through the existing `users` table; never trust user IDs supplied by the client.
4. Add owner-scoped endpoints for:
   - user bootstrap/profile read;
   - goals: create/get/list;
   - commitments: create draft/get/list/activate.
5. Preserve existing idempotency requirements using an `Idempotency-Key` request header on writes.
6. Translate domain/persistence failures to stable client errors without leaking database details.
7. Add request/response schema validation at the HTTP boundary.

**Likely files:**
- Create: `apps/api/src/server.ts`, `apps/api/src/app.ts`, `apps/api/src/config.ts`, `apps/api/src/http/*`, `apps/api/test/http/*`
- Modify: `apps/api/package.json`, `apps/api/src/persistence/service.ts` only if a read/list method is genuinely required

**Validation:**
```bash
npm run typecheck
npm test
```
Add integration tests proving unauthenticated requests are rejected, an identity cannot read another user's data, malformed requests do not write state, and an idempotent retry returns the original response.

**Exit criterion:** An authenticated client can complete `create goal → create commitment draft → activate`, with private records correctly scoped to that identity.

## Stage 4 — Complete the three proof paths privately

**Outcome:** Each accepted commitment can reach a clear qualified, not-qualified, challenged, or expired outcome without persisting unnecessary raw evidence.

**Work:**
1. Add the remaining private verification schema: verification attempts, normalized proof results, provider connection references, verifier relationships/invitations/responses, and audit metadata—following the accepted backend spec.
2. Implement the objective weekly-savings evaluator from indexed vault deposits.
3. Define and implement a `ProofAdapter` interface and a single activity-count adapter. Document provider scopes, accessed fields, normalized claim, retention, and deletion behavior. Store only minimal normalized evidence; raw evidence defaults to not stored.
4. Implement private social-verification invitations and response collection. Never place relationships or verifier identities onchain.
5. Implement bounded trust/confidence calculation behind an interface, with deterministic fixtures. Low-confidence cases must become “Additional verification required”, not punitive accusations.
6. Add lifecycle commands that progress active commitments through awaiting proof, verifying, challenged, qualified/not-qualified, expired, and settled.
7. Add worker/job idempotency, retry policy, and time-window scheduling for verification operations.

**Likely files:**
- Create: `packages/proof-adapters/*`, `packages/trust-engine/*`, `apps/api/src/verification/*`, `apps/api/src/social-verification/*`, migrations and tests
- Modify: `apps/api/src/domain/commitments/*`, `apps/api/src/db/schema.ts`, `apps/api/src/persistence/*`

**Validation:**
```bash
npm run typecheck
npm test
```
Add tests for every state transition, adapter failure/retry, no raw-provider payload persistence, social relationship ownership, reciprocal/weak evidence challenges, and expiry behavior.

**Exit criterion:** Deterministic fixtures complete all three commitment paths and prove the privacy-minimization rules.

## Stage 5 — Submit bounded qualifications and expose rewards

**Outcome:** A positive private verification can create one opaque onchain reward entitlement, which the user can claim as Monad USDC.

**Work:**
1. Add a contract-facing qualification service with a narrow interface: recipient, active epoch, capped TWAB, confidence BPS, reward-weight BPS, and opaque `bytes32` qualification ID. It must never accept or compute a backend-specified payout amount.
2. Generate/store an opaque, versioned settlement identifier; ensure it contains no semantic commitment, provider, or verifier information.
3. Add reward-submission persistence with idempotency, transaction status, event indexing, and retry/final-failure policy.
4. Calculate TWAB from indexed vault state under a specified, tested sampling/window policy. Do not rely on unindexed client balance data.
5. Add epoch administration/runbook support for prefunding and opening only the accepted demo epoch parameters.
6. Add web reward status and recipient-only claim flow. Show reward USDC as separate from savings/yield.
7. Test that a compromised qualifier can create only capped, prefunded entitlements and has no vault/principal authority.

**Likely files:**
- Create: `apps/api/src/rewards/*`, `apps/api/src/chain/reward-indexer.ts`, migrations, `apps/web/src/features/rewards/*`
- Modify: `apps/api/src/db/schema.ts`, `apps/api/src/domain/commitments/*`, contract ABI boundary

**Validation:**
```bash
npm run typecheck
npm test
forge test --root packages/contracts
```
Add an end-to-end controlled-chain test for verified commitment → qualification registration → recipient-only claim, plus replay, wrong-recipient, cap, and insufficient-funding failures.

**Exit criterion:** A qualified user receives a real bounded claim entitlement; no backend path can access vault funds or choose an arbitrary payout.

**Outcome:** Kept demonstrates both sponsor integrations in the accepted, safety-preserving architecture.

**Work:**

2. Create user-facing automation setup, pause, revoke, and status flows. Policy creation must bind Monad, the Kept vault, `depositAutomatically(uint256)`, canonical USDC, amount cap, and caller-owned receiver/spender semantics.

4. Implement and demonstrate the deliberately out-of-policy delegated action being rejected by policy and/or vault enforcement.
5. Confirm the current official Aurora / NEAR Intents API before coding; implement only the two-stage path: origin asset → user’s Monad USDC → sponsored vault deposit.
6. Persist quotes, transfer identifiers, status transitions, recovery/refund references, and destination settlement confirmation. Never claim “added” until the Monad destination and vault deposit are separately settled.
7. Present both integrations as normal “Automatic saving” and “Add money” product flows, with material authorization/liquidity consequences clearly disclosed but without bridge/solver/gas jargon.

## Sequencing rules

- Stages 1 and 2 can proceed in parallel after agreeing the HTTP contract.
- Stage 3 must precede the objective weekly-savings evaluator in Stage 4 and TWAB/reward work in Stage 5.
- Stage 4 can begin with deterministic fixtures before external provider credentials are available.
- Stage 5 must precede a full Stage 7 demo, but the basic savings UI from Stages 2–3 can be demoed earlier.
- Stage 6 begins only after checking current official Privy and Intents documentation; do not build against stale SDK assumptions.
- Avoid a separate microservice, commitment contract, treasury contract, or offchain principal ledger at every stage.

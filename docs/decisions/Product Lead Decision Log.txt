DECISION ID: KEPT-PL-009
Date: 08-Sep-2026
Title: Layered enforcement for delegated automatic saving
Status: ACCEPTED
Decision: Kept's MVP will enforce delegated automatic saving through layered controls. Privy policy will restrict chain, destination, function, receiver and per-transaction amount. KeptSavingsVault will strictly enforce no more than one delegated automatic deposit per wallet every rolling seven days. The backend scheduler remains a trigger only and is never an authorization boundary.
Reason: Current public Privy stateful-policy windows are limited to 72 hours and are explicitly not strict against concurrent requests, so Privy alone cannot currently provide Kept's accepted weekly authorization guarantee.
Alternatives: Scheduler-enforced weekly rule; 72-hour rule presented as weekly; dynamically rotating policies; separate automation contract; weakening the MVP claim.
Affected teams: Contracts, Wallet/Intents, Backend, Privacy/Security, Product/UX, QA.
Implementation consequence: Add a minimal automation-specific vault entry point with strict seven-day cadence state. No fourth deployed MVP contract.
Context file to update: Kept-Privy-Implementation-Spec-07-Sep-2026.txt, Kept-MVP-Technical-Architecture-07-Sep-2026.txt, Product-Outline.txt.

DECISION ID: KEPT-PL-012

Status: ACCEPTED
Decision: Kept's MVP must independently bound both reward-oracle and delegated automatic-saving authority. RewardController may distribute only bounded pre-funded behavioural rewards and has no authority over saver principal or vault shares. Privy delegated policies must pin the authorized vault, function, amount, asset and user-controlled receiver/spender semantics so delegated actions cannot redirect funds.

Implementation consequence: Reward caps and role isolation become contract requirements; delegated transaction policy must bind receiver/spender; corresponding adversarial tests are required before MVP acceptance.

KEPT-PL-015 — Freeze MVP smart-contract topology

Status: ACCEPTED
Decision: Kept's MVP will deploy exactly three Kept contracts: ERC-4626 KeptSavingsVault, one AaveUSDCStrategy permanently bound to that vault deployment behind the IYieldStrategy code abstraction, and financially isolated RewardController. KEPT-PL-016 — MVP behavioural reward formula and settlement

Date: 08-Sep-2026
Title: Behavioural reward calculation and payout destination
Status: ACCEPTED
Decision: For qualified MVP commitments, RewardController calculates rewards from capped time-weighted eligible balance × epoch-specific reward rate × verification confidence × reward weight, then applies per-qualification, per-user-per-epoch and total-epoch caps. Qualification is binary for MVP; no partial completion scalar is introduced. Deployment-wide immutable hard ceilings bound all configurable epoch values. Rewards are claimable as native Monad USDC to the user's pre-bound Privy Monad wallet and are not automatically converted into vault shares.
Reason: This preserves the Product Outline's time-weighted/confidence-based economics while keeping the backend from specifying arbitrary payouts, bounding oracle compromise and maintaining strict financial separation between saver principal and behavioural treasury.
Alternatives: Backend-specified payout; continuous partial-completion rewards; automatic vault-share rewards; fixed flat reward.
Affected teams: Contracts, Backend, Economics, Privacy/Security, Product/UX, QA.
Implementation consequence: RewardController performs bounded fixed-point calculation; Backend submits qualification inputs rather than payout amounts; UX treats earned reward as separate USDC reward; Economics must supply concrete hard ceilings and epoch values.
Context file to update: Kept-MVP-Technical-Architecture-07-Sep-2026.txt, Kept-Behavioural-Reward-Economics-Framework-07-Sep-2026.txt, backend contract-facing spec, smart-contract acceptance criteria.
